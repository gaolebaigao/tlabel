# TLabel 标准偏航分析（v0.8.0）

**日期**: 2026-06-28  
**分析范围**: TLabel v0.8.0 全量源码审查（9,579行Python + 250行Schema + 1,883行文档）  
**目标**: 评估 TLabel 当前功能是否偏航于"触觉数据标注业内标准"的定位

---

## 二、偏航评估

### 🟢 不偏航（核心竞争力）

#### 1. 多传感器适配器体系（3,525行 / 37%）
**判断: 完全正确，这是标准的核心**

6个适配器覆盖了主流触觉传感器，`auto_detect_format()` 实现了"一个`load()`调用搞定一切"的承诺。这正是"标准"应该做的事——统一入口、统一输出。

- GelSight/Daimon/PaXini: 视觉式
- ToucHD: 阵列式
- VTouch: 事件式
- TLabel Format: 已有TLabel数据的直接加载

**结论**: 这是TLabel作为"事实标准"的根基，无需调整。

#### 2. 统一22维输出格式（tlabel_v2）
**判断: 正确，但需要文档跟上**

22维特征向量是目前TLabel最核心的标准化输出。每个维度有明确的物理语义，从 `contact` 到 `contact_transition` 覆盖了触觉标注的主要方面。

**问题**: `annotation-spec.md` 和 `tlabel-format.md` 都停在 v0.2.0，与实际 v0.7.0+ 的代码完全不同步。这是目前最大的偏航点——**标准文档不标准**。

#### 3. 多格式导出（JSON/CSV/HDF5）
**判断: 标准工具的标配功能**

一个标准工具必须能输出主流格式。JSON（人类可读）、CSV（表格分析）、HDF5（科学计算）——三个格式覆盖了所有使用场景。正确。

#### 4. FTP-1/MTTS Zarr导出（v0.8.0新增）
**判断: 战略正确，卡位前沿**

直接对接全球首个通用触觉基础模型的数据格式，让TLabel成为FTP-1生态的"数据层入口"。这不是偏航，是精准卡位。

#### 5. LeRobot格式转换
**判断: 正确，对接HuggingFace生态**

LeRobot是当前机器人学习领域最活跃的框架之一，支持它是必要的生态位。

---

### 🟡 轻微偏航（需要调整定位）

#### 6. AI预标注引擎（1,210行 / 13%）
**判断: 功能本身有价值，但不应该是"标准"的核心**

`PredictEngine` + `MLEngine` + `PostProcessor` 实现了规则推断、梯度提升ML、HMM相位检测、时序后处理。这套东西很酷，用户也确实用得到，但——

**一个"格式标准"不需要自带ML引擎。** 就像COCO标准不自带目标检测模型，KITTI不自带深度估计网络一样。

**建议**: 保持功能，但在定位上明确区分：
- **TLabel Core**（标准层）: 适配器 + 格式定义 + 导出 → 这是"标准"
- **TLabel Tools**（工具层）: 预标注 + 质量评分 + 批处理 → 这是"辅助工具"

#### 7. 数据质量评分（327行）
**判断: 对标国标的想法很好，但"国标"本身还不存在**

`QualityScorer` 对标的是《具身智能数据质量规范》TC28/SC42，但这个国标还在制定中。评分逻辑（物理一致性30% + 时序平滑度25% + 完整性25% + 覆盖率20%）是合理的，但——

**问题**: 如果TLabel想成为"标准"，那质量评分的权重定义本身就应该由标准来定，而不是TLabel自己定。现在是"TLabel定义了标准，TLabel也定义了什么符合标准"——这有既当运动员又当裁判的嫌疑。

**建议**: 暂时保留，但未来应将评分规则抽象为可配置的标准规范（类似 `.tlabel-quality-spec.json`），让社区/标准组织来定义权重。

#### 8. 批处理器（263行）
**判断: 实用功能，但不属于"标准"范畴**

`BatchProcessor` 解决的是工程效率问题，不是标准化问题。它很有用，但就像 `pandas` 不是数据格式标准一样。

**建议**: 同AI预标注，归入"TLabel Tools"。

---

### 🔴 明确偏航（需要修正）

#### 9. 文档与代码严重脱节
**判断: 这是最致命的偏航**

| 文档 | 标注版本 | 实际代码版本 | 差距 |
|------|----------|------------|------|
| `annotation-spec.md` | v0.2.0 | v0.7.0+ | 5个小版本 |
| `tlabel-format.md` | v0.2.0 | v0.7.0+ | 5个小版本 |
| `tlabel-schema.json` | v0.7.0 | v0.7.0+ | ✅ 同步 |

**v0.2.0 → v0.7.0 之间发生了什么文档未覆盖的变化**:
- v0.3.0: Cascade联动规则、Patch修正机制
- v0.4.0: 22维特征完整定义（v0.2.0只有11维）
- v0.5.0: AI预标注引擎、HMM相位检测
- v0.6.0: 单位标准化、物理量语义修正
- v0.7.0: `sensor_profile`、`calibration_params`、`force_magnitude`废弃
- v0.8.0: FTP-1/MTTS导出、功能区定义

**如果一个"标准"的文档和实现不一致，那它就不是标准，只是一个有人用的工具。**

#### 10. Schema与代码的实际输出不一致
**判断: Source of Truth不清晰**

`tlabel-schema.json` (v0.7.0) 定义了 `sensor_profile`、`calibration_params` 等字段，但实际代码中：
- `sensor_profile` 在 `types.py` 中是可选字段，大部分适配器不填充
- `calibration_params` 同样是空字典
- `capabilities` 的实际内容与schema描述不完全匹配

**问题**: 当别人试图按照schema实现自己的TLabel解析器时，会发现schema和实际数据对不上。这是标准的致命伤。

#### 11. UI占比过重
**判断: 头重脚轻**

`viewer/templates.py` (1,405行) 比 `core/types.py` (784行) 大了近一倍。一个"标准工具"的UI代码比核心数据结构还大，说明产品重心在偏移。

不是说UI不重要——对标注工具来说，好的UI是用户体验的关键。但如果目标是"业内标准"，那标准的价值在于**格式定义和互操作性**，而不在于UI好不好看。

**风险**: 如果竞争对手出了一个"格式兼容TLabel但UI更好"的工具，TLabel的UI优势就变成了沉没成本。

## 三、风险矩阵

| 风险项 | 严重度 | 紧迫度 | 说明 |
|--------|--------|--------|------|
| 文档停在v0.2.0 | 🔴 致命 | 🔴 立即 | 别人无法按文档实现兼容 |
| Schema-Code不一致 | 🔴 致命 | 🔴 立即 | 互操作性无法保证 |
| 无版本治理流程 | 🟡 中等 | 🟡 近期 | 未来改格式会失控 |
| 功能蔓延（ML/Quality/Batch） | 🟡 中等 | 🟢 不急 | 不影响标准定位，但需要分层 |
| UI过重 | 🟢 低 | 🟢 不急 | 当前阶段UI是竞争力 |
| 无Conformance Test Suite | 🟡 中等 | 🟡 近期 | 无法验证第三方实现是否兼容 |

## 四、优先行动建议

### P0 — 立即做（本周）

1. **同步 `annotation-spec.md` 到 v0.7.0+**
   - 补充 cascade规则、patch机制、22维完整定义
   - 补充 sensor_profile、calibration_params 的语义
   - 补充 force_magnitude → deformation_magnitude 的废弃说明

2. **同步 `tlabel-format.md` 到 v0.7.0+**
   - 更新JSON结构示例（实际从代码生成）
   - 补充 episodes/frames 的完整字段说明
   - 补充 capabilities 的实际声明规则

3. **Schema-Code对齐验证**
   - 写一个脚本：用每个适配器生成示例数据，自动验证是否符合schema
   - 找出不一致的地方，修代码或修schema（以代码为准，因为代码是实际在用的）

### P1 — 近期做（1-2周）

4. **添加Schema Validation**
   - `load()` 时可选校验（`validate=True`）
   - `export` 时强制校验
   - 校验失败给出明确的错误信息和修复建议

5. **发布 Conformance Test Suite**
   - 一组标准测试数据 + 期望输出
   - 第三方可以验证自己的实现是否兼容TLabel
   - 这是"标准"区别于"工具"的关键一步

6. **分层文档结构**
   ```
   docs/
   ├── spec/              ← 标准规范（严格版本控制）
   │   ├── annotation-spec.md
   │   ├── format-spec.md
   │   └── conformance.md
   ├── tutorials/         ← 使用教程
   ├── api/               ← API文档
   └── extensions/        ← 扩展功能（ML/Quality/Batch）
   ```

### P2 — 中期做（1-2月）

7. **写维度设计论文/白皮书**
   - 为什么是这22维？设计依据是什么？
   - 与MTTS的21功能区如何映射？
   - 与FTP-1的数据需求如何对齐？
   - 这不是学术论文，是"标准文档"的学术化表达

8. **建立版本治理RFC流程**
   - 格式变更需要经过RFC（Request for Comments）
   - 社区可以提案、讨论、投票
   - 这是从"一个人的项目"到"社区标准"的关键转变

9. **sensor_profile 实际填充**
   - 为每个支持的传感器填写真实的物理标定参数
   - 让 `calibration_params` 不再是空字典
   - 这是从"语义统一"到"物理统一"的跨越

## 五、总结判断

**TLabel当前的功能丰富度远超同类工具，但"标准文档"停留在v0.2.0。**

这不是功能偏航——功能本身都在正确的方向上。真正的问题是**"身体已经18岁，身份证还写着5岁"**。

核心矛盾：
- 代码已经到了v0.8.0，文档还在v0.2.0
- Schema定义和实际代码输出不完全一致
- 没有版本治理流程，格式变更全靠个人决定

**好消息是：这些问题都是文档和流程层面的，不需要重写代码。** 修复成本远低于开发新功能的成本。

**建议优先级**: 先修文档（P0）→ 再加验证（P1）→ 最后建治理（P2）。

**一句话**: TLabel不缺功能，缺的是把已有的东西说清楚、写明白、管起来。
