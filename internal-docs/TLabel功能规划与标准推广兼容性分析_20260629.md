## 一、现有功能全景

### 1.1 UI 面板功能（Panel）

| Tab | 功能 | 交互方式 |
|-----|------|----------|
| 📝 标注 | 时间轴浏览、22维雷达图、帧详情、单帧修正、区间批量修正、导出（JSON/CSV/HDF5） | 点击/拖拽时间轴，输入框修改数值 |
| 🎬 Episode | Episode列表、语义标注（outcome/manip_type/difficulty/notes） | 下拉框选择 |
| 📊 质量评分 | 四维度评分仪表盘（物理一致性30% + 时序平滑25% + 完整性25% + 覆盖率20%）、等级徽章(A/B/C/D)、警告列表 | 只读展示 |
| 📈 统计 | 各通道均值/标准差/极值/分位数/缺失率 | 表格排序 |
| 🚀 导出(FTP-1) | 传感器选择(7种)、功能区勾选(21区域+预设)、Zarr导出预览 | 下拉框+复选框，生成Python命令 |

| **批处理** | `BatchProcessor` — 多Episode批量评分+导出 | 263行 |
| **可视化** | Jupyter Panel + 批量仪表盘 | 2,080行 |

## 二、用户实际需求分析

### 2.1 用户画像

基于PyPI数据（~470次真实下载，Linux 92%）推断，TLabel的用户画像是：

| 用户类型 | 占比(估) | 核心需求 | 停留时间 |
|----------|---------|----------|----------|
| **好奇型** | ~40% | pip install → demo → 看看长啥样 → 走人 | < 5分钟 |
| **任务型** | ~45% | "我有一批GelSight数据要标注" → 加载 → 标注 → 导出 | 10-30分钟/episode |
| **集成型** | ~10% | "我要把TLabel接入我的训练pipeline" → API调用 → 格式转换 | 1-2小时 |
| **贡献型** | ~5% | "我要加一个新传感器/功能" → 读源码 → 提PR | 持续 |

### 2.2 用户真正想做的事（按优先级排序）

1. **"让我看到我的数据"** — 可视化原始触觉信号
2. **"让我快速标注"** — 在合理时间内完成一个Episode的标注
3. **"让我导出能用的数据"** — 输出我的模型/训练框架需要的格式
4. **"让我别犯错"** — 避免格式错误、物理不一致
5. **"让我管理我的数据集"** — 多Episode浏览、筛选、搜索

### 2.3 用户**不**想做的事

1. 学习22维特征空间的理论
2. 理解什么是"sensor-agnostic annotation schema"
3. 手动填写 raw_unit 和 physical_semantics
4. 关心TLabel是不是"标准"
5. 读超过一页的文档

## 三、功能-需求差距分析

### 3.1 ✅ 已满足的需求

| 需求 | 现有功能 | 评价 |
|------|----------|------|
| 加载多传感器数据 | `tlabel.load()` 自动识别 | ⭐ 优秀，核心竞争力 |
| Demo体验 | `tlabel.demo()` + `data.review()` | ⭐ 优秀，30秒体验闭环 |
| 基础导出 | JSON / CSV / HDF5 | ✅ 够用 |
| FTP-1格式导出 | `export_ftp1()` + Panel导出Tab | ✅ 前沿卡位 |
| 基础标注修正 | 单帧patch + 批量batch_patch | ✅ 基本够用 |

### 3.2 🔴 关键缺失

| 缺失功能 | 用户痛点 | 严重程度 |
|----------|----------|----------|
| **原始数据可视化** | 用户看不到自己的传感器图像/力曲线！Panel只显示22维特征雷达图，不显示原始触觉图像。对于GelSight用户来说，"我看不到我的凝胶图像怎么标注？" | 🔴 致命 |
| **交互式区域标注** | 22维全是数值输入框，没有画布式的交互。用户无法在触觉图像上圈选接触区域、画滑移方向 | 🔴 严重 |
| **多Episode数据集管理** | 只能一个Episode一个Episode地打开，没有数据集浏览器、搜索、筛选 | 🔴 严重 |
| **标注进度追踪** | 不知道一个数据集里哪些Episode已标注、哪些未标注 | 🟡 中等 |
| **快捷键标注** | 标注一个接触帧需要：找到帧 → 找到contact字段 → 输入1 → 确认。太高频的操作需要一键完成 | 🟡 中等 |
| **导入已有标注** | 只能从零开始标注，不能导入之前的标注结果继续编辑 | 🟡 中等 |

### 3.3 🟡 有但不够好的功能

| 功能 | 问题 | 用户视角 |
|------|------|----------|
| AI预标注 | 有PredictEngine但Panel里没有集成"一键AI标注"按钮，需要写Python代码 | "我以为是可视化工具，结果要我写代码？" |
| 质量评分 | 只给分数和警告，不给修复建议 | "你告诉我质量差，但怎么修？" |
| Episode标注 | 只有outcome/manip_type/difficulty三个字段，不够灵活 | "我想标注抓取力等级、物体材质…没地方填" |
| 统计Tab | 只是describe()的表格展示，没有可视化 | "我以为有图表，结果是个表格" |
| FTP-1导出Tab | 生成Python命令而不是直接导出 | "我为什么要复制命令去终端执行？不能直接导出？" |

## 四、核心矛盾：标准 vs 工具

### 4.1 矛盾的本质

```
标准思维：定义格式 → 让人遵守 → 成为标准
工具思维：解决痛点 → 让人喜欢 → 自然形成依赖 → 格式成为事实标准
```

TLabel 目前的定位更接近**标准思维**——先定义了22维格式，再做工具来承载它。但用户不会因为"你的格式好"来用你的工具，他们只会因为"你的工具好用"来用你的工具。

### 4.2 历史经验

| 成功案例 | 路径 | 关键 |
|----------|------|------|
| COCO | 先做好标注工具(MS COCO Viewer) → 格式因工具流行而成标准 | **工具好用 → 格式自然传播** |
| JSON | 解决了XML的痛点（人类可读性） → 开发者自发采用 | **解决真实痛点** |
| Docker | 解决了"在我机器上能跑"的痛点 → 容器格式成为事实标准 | **工具价值先于标准价值** |
| Markdown | 解决了富文本编辑的复杂度 → 写作体验驱动采用 | **简单即正义** |

| 失败案例 | 路径 | 教训 |
|----------|------|------|
| XML Schema | 先定标准 → 工具跟不上 → 没人用 | 没有好用的工具，标准是空文 |
| RDF/OWL | 学术上完美 → 实际太复杂 → 被JSON Schema取代 | 复杂度是标准的敌人 |

### 4.3 TLabel的现状定位

```
当前状态：
  标准成熟度: ████████░░ 80%（22维格式、白皮书、schema都有了）
  工具成熟度: █████░░░░░ 50%（能用，但不好用；能标注，但不够高效）

理想状态：
  标准成熟度: ██████████ 100%
  工具成熟度: █████████░ 90%（先让工具足够好用，标准自然跟随）
```

**当前最大的风险不是标准不够完善，而是工具不够好用导致用户流失。**

## 五、兼容策略："工具即标准"

### 5.1 核心原则

> **用户不需要知道TLabel是一个"标准"。他们只需要知道这是一个好用的标注工具。当他们导出的数据天然符合TLabel格式时，标准已经在他们不知道的情况下被采纳了。**

这叫做 **Transparent Standard** — 对用户透明的标准。

### 5.2 三层架构

```
┌─────────────────────────────────────────────┐
│              用户感知层（工具）                │
│  "我用TLabel标注触觉数据，它很好用"           │
│                                              │
│  · 原始数据可视化（图像/力曲线/热力图）        │
│  · 交互式标注（画布标注、快捷键、拖拽）        │
│  · 数据集管理（多Episode浏览、筛选、进度）     │
│  · AI辅助标注（一键预标注、智能建议）          │
│  · 格式导出（用户选目标格式，不需要知道内部格式）│
├─────────────────────────────────────────────┤
│              标准层（用户无感知）              │
│  用户每一次标注操作，都在生成符合TLabel的数据   │
│                                              │
│  · 22维特征空间（内部表示，用户看到的是语义名） │
│  · Cascade规则（标注时自动执行，用户无感知）   │
│  · Per-feature metadata（自动生成，用户不填） │
│  · Capability声明（根据传感器自动生成）        │
│  · 物理一致性（实时检查+自动修正）             │
├─────────────────────────────────────────────┤
│              生态层（开发者/研究者感知）        │
│  "TLabel格式是触觉数据的通用交换格式"          │
│                                              │
│  · Format Spec（严格的版本控制文档）           │
│  · Conformance Test Suite（兼容性验证）       │
│  · RFC治理流程（社区参与标准演化）             │
│  · 与其他框架的集成（FTP-1、LeRobot、HuggingFace）│
│  · TLabel-Bench（标准化评测基准）              │
└─────────────────────────────────────────────┘
```

### 5.3 具体策略

#### 策略1：标准下沉为内部实现

| 标准概念 | 用户看到的 | 内部实际发生的 |
|----------|-----------|---------------|
| 22维特征空间 | "接触/滑移/力度/纹理…" 等语义化按钮 | 写入tlabel_v2特征向量 |
| Cascade规则 | 设置"非接触"后，力/滑移字段自动灰掉 | 物理一致性自动执行 |
| raw_unit / physical_semantics | 导出时自动附带 | 用户不需要填，系统根据传感器+特征自动填充 |
| Capability声明 | 加载时自动检测传感器能力 | 生成capabilities字典 |
| FTP-1兼容 | 选择"导出为FTP-1格式"按钮 | tlabel_to_ftp1()转换 |

**核心：标准是引擎，不是方向盘。用户看到的是方向盘（工具），引擎（标准）在引擎盖下面。**

#### 策略2：先投资源到用户感知层

**当前资源分配估算：**

```
标准相关（schema/spec/whitepaper/RFC）:  ~30%
工具功能（新功能开发）:                   ~25%
UI/UX优化:                              ~25%
传感器适配器:                            ~20%
```

**建议调整为：**

```
工具功能 + UI/UX优化:                    ~50%  ← 大幅提升
传感器适配器:                            ~20%
标准相关:                                ~20%  ← 维持，不再加码
文档/教程:                              ~10%  ← 补齐欠账
```

#### 策略3：功能优先级的判断标准

用"TLabel功能判断原则"来筛选：

| 判断问题 | 如果答案是... |
|----------|--------------|
| 这个功能能防止用户犯错吗？ | ✅ 做 |
| 这个功能能帮用户做决策吗？ | ✅ 做 |
| 这个功能能减少用户困惑吗？ | ✅ 做 |
| 这个功能能加快标注速度吗？ | ✅ 做（优先级高） |
| 这个功能是为了让标准更完善吗？ | 🤔 放后面，除非用户也能感知到 |
| 这个功能是为了讨好审稿人/评审吗？ | ❌ 不做 |

## 六、功能路线图建议

### Phase 1: 核心标注体验（1-2周）— 让用户"能用"

| 功能 | 目的 | 复杂度 | 标准关联 |
|------|------|--------|----------|
| **原始数据可视化** | 在Panel里显示触觉图像/力曲线 | 中 | 无直接关联，但用户需要看到原始数据才能标注 |
| **快捷键标注** | C=标记接触, S=标记滑移, Space=下一帧 | 低 | 无 |
| **时间轴框选标注** | 在时间轴上拖拽选择区间 → 批量设置标签 | 中 | 无 |
| **AI预标注一键按钮** | Panel里加个"🤖 AI预标注"按钮，不用写代码 | 低 | 无 |
| **FTP-1直接导出** | 不要生成Python命令，直接导出Zarr文件 | 低 | 标准生态关联 |

### Phase 2: 数据管理能力（2-4周）— 让用户"好用"

| 功能 | 目的 | 复杂度 | 标准关联 |
|------|------|--------|----------|
| **数据集浏览器** | 多Episode列表、缩略图、状态标记 | 高 | 无 |
| **标注进度面板** | 已标注/未标注/需审核的Episode统计 | 中 | 无 |
| **导入已有标注** | 加载之前导出的JSON/CSV继续编辑 | 低 | 验证TLabel格式的可逆性 |
| **搜索/筛选** | 按outcome/difficulty/传感器类型筛选Episode | 中 | 无 |
| **数据集级统计** | 整体质量分布、标注进度、特征分布图 | 中 | 无 |

### Phase 3: 质量与协作（1-2月）— 让用户"放心"

| 功能 | 目的 | 复杂度 | 标准关联 |
|------|------|--------|----------|
| **质量修复建议** | 不只是告诉用户质量差，还要告诉他怎么修 | 中 | 标准层的物理一致性规则 → 转化为修复建议 |
| **标注模板** | 预设常见任务的标注模板（抓取/滑动/旋转） | 低 | 可以引导用户使用标准字段 |

| **多用户标注** | 多人标注同一数据集 + 一致性评估 | 高 | 长远来看对标准推广有价值 |

### Phase 4: 标准生态（持续）— 让用户"离不开"

| 功能 | 目的 | 复杂度 | 标准关联 |
|------|------|--------|----------|

| **Conformance Test Suite** | 发布标准兼容性测试集 | 中 | 🔴 标准核心 |
| **Format Spec v0.8.0** | 文档与代码同步 | 低 | 🔴 标准核心（已经在做） |
| **社区RFC** | 公开RFC流程，让社区参与标准演化 | 低 | 🔴 标准核心 |

## 七、标准推广的正确姿势

### 7.1 不要说"我们是标准"

| ❌ 错误说法 | ✅ 正确说法 |
|------------|-----------|
| "TLabel是触觉数据标注的行业标准" | "TLabel让你一个工具搞定所有传感器" |
| "我们的22维特征空间定义了统一格式" | "标注一次，到处使用——GelSight、FTP-1、LeRobot全兼容" |
| "我们的schema符合XX国标" | "导出的数据可以直接用于FTP-1微调" |
| "我们定义了触觉数据的COCO" | "再也不用为每个传感器写不同的标注脚本了" |

### 7.2 标准推广的正确路径

```
Step 1: 让10个人觉得"TLabel好用" → 靠工具质量
Step 2: 让100个人用TLabel导出数据 → 靠生态集成（FTP-1/LeRobot）
Step 3: 让1000个人写论文引用TLabel → 靠TLabel-Bench + 学术影响力
Step 4: 让10000个人知道TLabel格式 → 靠社区 + 教程 + 口碑
Step 5: 让标准组织参考TLabel格式 → 靠事实上的市场份额
```

**当前在 Step 1 → Step 2 的过渡阶段。** 还没有足够的人觉得"好用"，谈标准推广为时尚早。

### 7.3 FTP-1 合作的标准推广价值

FTP-1 Issue #2 是一个正确的方向，但要注意定位：

| ❌ 定位 | ✅ 定位 |
|--------|--------|
| "TLabel想成为FTP-1的官方标注标准" | "TLabel可以帮FTP-1用户更方便地准备训练数据" |
| "我们的格式和你们的MTTS等价" | "我们已经实现了MTTS导出，你的用户可以一键转换" |
| "让我们一起制定标准" | "我们可以为FTP-1写一个数据准备教程" |

**先成为FTP-1生态的有用工具，再谈标准层面的合作。**

## 八、关键结论

### 8.1 标准与工具的关系

> **标准不是目标，是结果。**
>
> 工具好用 → 用户多 → 数据格式被广泛使用 → 成为事实标准。
>
> 跳过"工具好用"直接推"标准"，就像跳过产品直接推品牌——空中楼阁。

### 8.2 当前优先级

1. **最紧迫**：补齐原始数据可视化 + 交互式标注 — 这是标注工具的基本功
2. **次紧迫**：文档与代码同步（P0偏航修复已在做）
3. **可以缓**：标准治理、Conformance Test Suite — 等用户量上来再推
4. **不要做**：为了标准完整性而增加用户不需要的功能

### 8.3 一句话总结

> **让标准成为工具的自然产物，而不是工具的设计目标。用户标注数据的每一秒，都在不知不觉中生产符合标准的数据——这才是标准推广的最高境界。**
